# 버그 티켓 원인 진단 (Defect Analysis)

버그·장애·데이터 정합성·튜닝 티켓의 분석 단계에 적용한다.
**원인 규명이 곧 요건 분석이다** — 원인을 모르면 "무엇을 고칠지"를 정의할 수 없다.

## 철칙 (Iron Law)

```
근본 원인을 규명하기 전에는 수정안을 제시하지 않는다
```

- 증상 대응 수정은 실패로 간주한다 — 재발하고, 진짜 원인을 가리고, 신뢰를 잃는다.
- "일단 이렇게 고쳐보고 지켜보자"는 이 철칙 위반이다.
- 급할수록 이 철칙이 더 중요하다 — 체계적 진단이 추측-수정 반복(thrashing)보다 **빠르다**.

## Phase 1 — 근본 원인 조사

1. **에러 메시지·로그 정독**: 스택트레이스를 끝까지 읽는다. 라인 번호·에러 코드·발생 시각을 기록한다. 에러 문구가 답을 그대로 담고 있는 경우가 많다.
2. **일관 재현**: 정확한 재현 절차를 확보한다. 매번 재현되는가? 재현이 안 되면 추측하지 말고 데이터를 더 모은다.
3. **최근 변경 확인**: 배포·커밋·설정·의존성 변경 이력과 증상 시작 시점을 대조한다.
4. **다층 시스템 증거 수집**: 여러 컴포넌트를 거치는 시스템(화면 → API → 서비스 → DB → 배치)이면, 수정안을 생각하기 전에 **각 경계에서 들어간 데이터와 나온 데이터를 확인**한다 — 로그·DB 조회·모니터링 등 프로젝트가 보유한 수단으로. 어느 층에서 깨지는지를 증거로 특정한 뒤, 그 층만 파고든다.
5. **데이터 흐름 역추적**: 잘못된 값을 발견한 지점이 아니라 그 값의 **발원지**까지 거슬러 올라간다. 증상 지점 수정은 발원지를 남긴다.

## Phase 2 — 패턴 비교

1. 같은 코드베이스에서 **정상 동작하는 유사 사례**를 찾는다 (같은 패턴의 다른 화면·쿼리·배치).
2. 정상과 비정상의 차이를 **전수 나열**한다 — "그건 상관없겠지"를 금지한다. 사소해 보이는 차이가 원인인 경우가 흔하다.
3. 의존 요소를 확인한다: 설정, 환경, 데이터 전제, 실행 순서.

## Phase 3 — 가설 검증

1. **단일 가설을 명문화**한다: "X가 원인이라고 본다. 근거는 Y" — 막연하지 않게, 구체적으로.
2. **최소 검증**: 가설을 확인하는 가장 작은 조회·재현·실험을 수행한다. 한 번에 한 변수만.
3. 기각되면 **새 가설**을 세운다 — 기각된 가설 위에 검증을 쌓지 않는다.
4. 모르면 "모른다"고 기록한다. 아는 척 단정이 가장 나쁘다 — 이후의 모든 판단을 오염시킨다.

## 산출물 — '원인 분석' 기록 항목

티켓 문서(호스트 지침이 정한 위치)의 원인 분석 섹션에 기록한다:

- **증상** / **재현 절차** / **근본 원인** / **증거**(로그·데이터·코드 위치) / **영향 범위** / (있다면) **잔여 확인 사항**
- 각 항목에 확인된 사실 / 추정 을 구분해 표기한다.
- 원인 확정 후 → `requirement-refinement.md`로 합류해 **수정 요건**(무엇을 어떻게 고칠지, 어디까지 고칠지)을 정의한다.

## Red Flags — 이 생각이 들면 Phase 1로 복귀

| 합리화 | 실제 |
|---|---|
| "단순 이슈라 절차 불필요" | 단순 버그에도 근본 원인은 있다. 절차는 단순 건에서 오히려 몇 분이면 끝난다 |
| "급하니 일단 고치자" | 첫 수정이 패턴을 만든다. 체계적 진단이 결국 더 빠르다 |
| "아마 X일 것" | 증상 관찰 ≠ 원인 이해. 증거로 확정하라 |
| "여러 개 한꺼번에 바꿔보자" | 무엇이 통했는지 알 수 없게 되고, 새 버그를 만든다 |
| "데이터만 보정하면 될 듯" | 보정은 증상 대응이다. 데이터가 왜 틀어졌는지가 원인이다 |

## 진짜 '원인 없음'인 경우

- 조사가 환경·타이밍·외부 요인으로 수렴하면: 조사 내역을 기록하고, 방어 처리(재시도·타임아웃·알림)와 모니터링 추가를 **수정 요건**으로 정의한다. 이것도 정당한 종결이다.
- 단, "원인 없음" 결론의 대부분은 조사 미완이다. 위 Phase를 다 돌았는지 먼저 확인한다.
