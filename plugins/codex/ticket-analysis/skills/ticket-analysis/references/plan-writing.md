# Plan 작성 (Plan Writing)

요건이 확정된 뒤, 구현자를 위한 실행 가능한 계획을 쓴다.

## 독자 가정 — 핵심 원칙

**"이 코드베이스를 전혀 모르는 숙련 개발자"가 읽고 그대로 실행할 수 있어야 한다.**

이 가정이 중요한 이유: 그 독자는 가상의 인물이 아니다 — 컨텍스트가 리셋된 미래의 자신, 팀의 다른 에이전트, 계획만 보고 판단하는 리뷰어가 모두 이 독자다. "나는 아니까"로 생략한 정보는 그들에게 존재하지 않는 정보다.

## 1. 파일 구조 먼저

- 태스크를 정의하기 전에, 생성/수정할 파일의 맵을 먼저 그린다: 파일별 책임 한 줄.
- 여기서 분해 결정이 확정된다 — 태스크는 이 구조 위에서 잘라야 경계가 깔끔하다.
- 기존 코드베이스의 패턴을 따른다. 계획과 무관한 구조 변경을 끼워 넣지 않는다.

## 2. 태스크 적정 크기

- 태스크는 **독립적으로 검증(리뷰) 가능한 최소 단위**다.
- 셋업·설정·문서화는 별도 태스크로 빼지 말고, 그것을 필요로 하는 태스크에 접어 넣는다.
- 분리 기준: 리뷰어가 "이 태스크는 승인, 저 태스크는 반려"를 **의미 있게** 판단할 수 있는 경계에서만 나눈다.

## 3. 태스크 구조 — 필수 항목

````markdown
### Task N: [이름]

**파일:**
- 생성: `정확한/경로/File.java`
- 수정: `정확한/경로/Existing.java` — 대상 메서드/쿼리 id, 검색 앵커 문자열, 대략 라인 범위

**Interfaces:**
- Consumes: 앞 태스크 산출물 중 이 태스크가 사용하는 것 — 정확한 시그니처
- Produces: 뒤 태스크가 의존하는 것 — 정확한 함수명·파라미터·반환 타입

**변경 내용:** 변경 전 / 변경 후 코드 블록

**검증:** 이 태스크만 독립적으로 확인하는 방법
````

- **Interfaces를 쓰는 이유**: 태스크를 나눠 실행할 때(다른 세션·팀원·서브에이전트) 구현자는 자기 태스크만 본다. 이 블록이 이웃 태스크와 주고받는 **유일한 계약**이다. 여기 없는 이름·타입은 구현자에게 존재하지 않는다.
- **수정 위치는 검색 앵커로**: 라인 번호는 틀어진다. `select id="mainList"`, `function searchOrder` 같은 앵커 문자열을 함께 적는다.

## 4. Global Constraints 헤더

- 계획 서두에 전 태스크 공통 제약을 둔다: 버전 하한, 네이밍·문구 규칙, 금지 사항.
- 요건 문서의 값을 **그대로 복사**한다 — 재해석·요약 과정에서 제약이 무뎌진다.
- 모든 태스크의 요구사항은 이 섹션을 암묵적으로 포함한다.

## 5. No-Placeholder 규칙

다음은 **계획 실패**로 간주한다 — 발견 즉시 실제 내용으로 교체:

- "TBD" / "추후 구현" / "상세는 나중에"
- "적절히 에러 처리" / "검증 추가" / "엣지 케이스 처리" (무엇을 어떻게 하는지 없이)
- "Task N과 유사하게" / "위와 동일" — 코드를 반복 기재하라. 구현자는 순서대로 읽지 않을 수 있다
- 코드가 필요한 스텝에 코드 블록 없이 설명만 있는 것
- 어느 태스크에도 정의되지 않은 타입·함수·메서드 참조

## 6. Self-review 3종 — 계획 완성 후 요건 문서를 다시 펴고

1. **요건 커버리지**: 요건 문서의 각 항목마다 "이걸 구현하는 태스크"를 지목할 수 있는가. 갭이 있으면 태스크를 추가한다.
2. **Placeholder 스캔**: §5의 패턴을 검색해 제거한다.
3. **시그니처 일관성**: 앞 태스크에서 정의한 이름·타입을 뒤 태스크가 정확히 같은 형태로 쓰는가. Task 3의 `clearLayers()`가 Task 7에서 `clearFullLayers()`로 등장하면 그것이 버그다.

발견 즉시 인라인 수정. 재리뷰 불필요 — 고치고 넘어간다.

## 7. 체크리스트·진행 표기

- 진행 상태 플래그·넘버링·의존 표기는 호스트 지침의 체계를 따른다. 없으면 `- [ ]` 체크박스를 쓴다.
