# 티켓 작업 절차 (Ticket Workflow)

티켓 선언부터 결과 보고까지의 전체 운영 절차. 본 문서가 티켓 워크플로의 **단일 소스**다.

## 1. 티켓 선언과 기준 티켓

- 사용자가 `현재 작업이 IT-11111`, `IT-11111 이어서 작업`처럼 `IT-\d+` 패턴의 티켓을 선언하면, 해당 티켓을 **기준 티켓**으로 설정한다.
- 티켓이 명시되지 않은 요청은 티켓 번호 확인을 1회 수행한 후 진행한다.

## 2. 티켓 컨텍스트 로드 (`ticket.md`)

- 기준 티켓이 설정되면 `~/.ai/tickets/<TICKET_ID>/ticket.md` 파일을 우선 확인한다.
- **파일이 있으면**: 내용을 추가 컨텍스트로 로드하고, `완료 항목` 이후의 `다음 작업`부터 이어서 진행한다. 단, 이어서 진행하는 작업이 체크리스트의 단계를 넘어가는 경우 사용자 컨펌을 받는다.
- **파일이 없으면**: Atlassian MCP를 통해 Jira 티켓을 분석하여 생성한다.
    - 분석 절차:
        1. 해당 티켓의 본문(description) 조회
        2. 해당 티켓의 댓글(comments) 전체 조회 — 댓글에서 합의된 내용이 본문에 미반영되었을 수 있으므로, **댓글의 최신 합의 사항을 본문보다 우선**하여 반영한다.
        3. 해당 티켓에 `relates to`로 연결된 이슈가 있으면 해당 이슈의 본문과 댓글도 함께 조회·분석한다.
        4. 본문 + 댓글 + 연결 이슈를 종합하여 최신 상태 기준으로 분석한다.
    - 생성 항목:
        - 작업 목표/범위 (Jira 분석 기반)
        - 현재까지 완료 항목
        - 다음 작업(미완료 항목)
        - 관련 메뉴/화면/모듈
        - 연결 이슈 요약 (`relates to` 이슈가 있는 경우)
    - 생성 완료 후 §4의 단계별 절차를 따른다.
- `ticket.md`의 표준 스키마는 `ticket-md-schema.md` 참조. 산출물 저장 경로 규칙은 `artifact-routing.md` 참조.

## 3. 도구 선택 (티켓 시작 시 1회 확인)

| 케이스 | 도구 | 기본 구성 | 비고 |
|---|---|---|---|
| 단순 티켓 (Controller 1~2개, 단일 모듈) | **단일 Claude** (§4 절차 그대로) | Lead 단독 | 팀 spawn 오버헤드 > 이득 |
| 본업 컨벤션 중심·모듈 다수·병렬 가능 | **`deft:agent-teams`** (모두 Claude opus) | BE/FE/QA 3인 (+옵션 designer) | 스킬이 페르소나·단계게이트 내장 |
| 다른 AI 시각·상호 리뷰·토론이 가치 있음 | **`deft:multi-round`** (Claude + Claudex/Codex mix) | 2~4인 회의 (consult/collaborate/debate 등) | 별도 인프라 불요 |
| 한 번에 답 비교만 | **`deft:multi-check`** | Codex + Claude + Gemini | 1회성 fan-out |

> 양방향 토론·페어/Trio·collaborate·signoff 회의는 `deft:multi-round`로 진행한다.

- 도구와 무관한 공통 규칙:
    - 본 §4 단계 게이트(요건분석/영향도/Plan/체크리스트 단계)는 **도구와 무관하게 강제**한다.
    - `ticket.md`는 **Lead 단독 writer** (표준 구조는 `ticket-md-schema.md`). 팀원은 본인 작업노트만 write.
    - 팀 운영 세부(페르소나·통신·연속성·팀원 이름 규칙)는 `deft:agent-teams` 스킬이 소유한다.

## 4. 단계별 작업 절차 및 승인 규칙

- 티켓이 선언되면, 일반 작업 절차(분석→영향도→변경 제안→승인→적용→검증→보고)를 아래와 같이 확장 적용한다.
- **각 단계 사이에서 사용자 승인 없이 다음 단계로 자동 진행하지 않는다.**

    1. **요건 분석** (일반 절차의 `분석`에 대응)
        - Jira MCP 분석 결과(§2)를 기본 전제로 삼는다.
        - Jira에 없는 추가 요건(Slack 논의, 기획 리뷰 전달사항 등)이 있으면 사용자로부터 수집하여 분석에 포함한다.
        - 방법론: 기능·개선 티켓은 `requirement-refinement.md`, 버그·튜닝 티켓은 `defect-analysis.md`를 먼저 적용 후 합류.
    2. **영향도 확인** (일반 절차의 `영향도 확인`에 대응)
        - `Controller → Service → Mapper XML → SQL` 순서로 영향도를 분석한다.
    3. → **사용자 컨펌**: 요건 분석 + 영향도 확인 결과를 제시하고 승인을 받는다.
    4. **Plan 수립 + 제안** (일반 절차의 `변경 제안`에 대응)
        - Plan 모드에 진입하여 구현 계획을 수립한다. 방법론: `plan-writing.md`.
        - 수립 과정에서 더 나은 방향이나 확인이 필요한 사항이 있으면 사용자에게 질문한다.
        - 계획 확정 후 티켓 `.md` 파일 하단에 `## 작업 계획` 섹션을 추가하고, 작업 순서를 체크리스트 형식으로 기록한다 (문법은 §5).
    5. → **사용자 승인**: Plan 및 제안 내용을 제시하고 승인을 받는다. 승인 시 확정된 Plan·체크리스트를 대화 내에서 사용자에게 바로 안내한다.
    6. **체크리스트 기반 작업 진행** (일반 절차의 `수정 적용` + `검증`에 대응)
        - 체크리스트의 각 단계를 순차적으로 진행한다.
        - 각 단계 완료 시 체크리스트를 갱신(`[O]`)하고, **사용자 컨펌 후** 다음 단계로 진행한다.
    7. **결과 보고** (일반 절차의 `결과 보고`에 대응)
        - 결과 보고 시, 티켓 메모 파일의 갱신 여부와 핵심 변경 사항을 함께 명시한다.

## 5. 체크리스트 문법

- 플래그:
    - `[ ]` 미진행 | `[>]` 진행중 | `[!]` 보류(사유 필수) | `[O]` 완료 | `[X]` 취소(사유 필수)
- 상위 항목 상태는 하위 항목 상태를 종합하여 결정한다:
    - 하위에 `[ ]`가 있으면 → 상위 `[ ]`
    - `[ ]` 없고 `[>]`가 있으면 → 상위 `[>]`
    - `[ ]`, `[>]` 없고 `[!]`가 있으면 → 상위 `[!]`
    - 하위 모두 `[O]` 또는 `[X]` → 상위 `[O]`
- 모든 항목에 넘버링하고, 기본 원칙은 번호 순서대로 순차 진행한다.
- 의존 관계 표기: 병렬 `← (N번과 병렬)` (양쪽 모두 표기), 후속 `← (N번 후속)`

## 6. 티켓 작업 셀프 체크리스트

작업 중·결과 보고 전 스스로 확인한다:

- [ ] 티켓 번호(`IT-\d+`)를 확인하고 현재 작업 컨텍스트로 설정했는가?
- [ ] `~/.ai/tickets/<TICKET_ID>/ticket.md`를 생성/조회하고, 완료 항목 이후 작업으로 이어서 진행했는가?
- [ ] 각 단계(요건 분석 → 영향도 → Plan → 체크리스트 각 단계) 전환 시 사용자 컨펌을 받았는가?
- [ ] 결과 보고 시 티켓 메모 업데이트 내용을 함께 기록했는가?
- [ ] 산출물을 `artifact-routing.md` 규칙대로 라우팅했는가?
