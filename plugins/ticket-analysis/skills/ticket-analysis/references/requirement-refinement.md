# 요건 정제 (Requirement Refinement)

티켓의 아이디어·요구를 구현 가능한 수준의 명확한 요건으로 정제한다.
목표는 "무엇을, 왜, 어디까지"에 대해 사용자와 같은 그림을 갖는 것이다.

## 0. 사전 조사 — 질문하기 전에 반드시

- **이슈 트래커**: 본문 + 댓글 전체 + 연결 이슈. 댓글에서 합의된 최신 내용이 본문과 다르면 **댓글이 우선**이다 (본문은 갱신이 늦는 경우가 많다).
- **코드베이스**: 관련 화면·모듈의 현재 구조, 유사 기능이 이미 따르는 패턴, 최근 커밋.
- 이유: 조사로 답할 수 있는 것을 물으면 대화가 늘어지고 신뢰를 잃는다. 질문은 조사로 좁혀지지 않는 갭에만 쓴다.

## 1. 스코프 판별 — 세부 질문보다 먼저

- 티켓이 **독립적인 하위 작업 여러 개**를 묶고 있다면(예: 화면 신설 + 배치 신설 + 정산 로직 변경), 세부 질문을 시작하기 전에 분해를 먼저 제안한다.
- 분해가 필요한 티켓에서 세부부터 파면, 나중에 버려질 디테일에 질문을 낭비하게 된다.
- 분해 후에는 첫 하위 작업부터 정제 사이클을 돈다. 하위 작업마다 요건 → 계획의 사이클을 독립적으로 갖는다.

## 2. 질문 규칙

- **한 메시지에 질문 하나.** 주제가 더 남았으면 다음 메시지에서 잇는다.
- 가능하면 **객관식**(선택지 2~4개 + 각각의 함의)으로 묻는다. 열린 질문도 허용.
- 묻는 대상: **목적**(왜 필요한가) · **제약**(무엇은 안 되는가) · **성공 기준**(무엇이 되면 완료인가).
- 묻지 않는 대상: 코드를 읽으면 아는 것, 이미 티켓에 적힌 것, 구현 디테일 중 어느 쪽이든 무방한 것.

## 3. 접근안 제시

- 접근안 **2~3개**를 각각의 트레이드오프와 함께 제시한다.
- **추천안을 먼저**, 추천 이유와 함께 제시한다. 나열만 하고 선택을 떠넘기지 않는다.
- **YAGNI**: 각 접근안에서 지금 필요 없는 기능을 덜어낸다.
- 기존 코드베이스의 패턴을 따르는 안을 우선 검토한다. 기존 코드에 이번 작업과 직접 관련된 문제가 있으면 targeted 개선을 안에 포함하되, 무관한 리팩토링은 제안하지 않는다.

## 4. 요건 정리·제시

- 섹션 분량은 복잡도에 비례시킨다 — 단순하면 몇 문장, 미묘하면 상세히.
- 긴 요건은 섹션 단위로 나눠 제시하고, 섹션마다 맞는지 확인받는다. 한 번에 전부 던지면 검토 품질이 떨어진다.
- 커버할 항목: 기능 동작, 데이터 흐름, 예외·에러 처리, 검증 방법.
- 각 항목에 확인된 사실 / 추정 / 미확인 을 구분해 표기한다.

## 5. Self-review 4종 — 요건 문서 작성 후 스스로 점검

1. **Placeholder 스캔**: "TBD", "추후", "적절히", 미완 섹션 → 지금 구체화하거나 미해결 결정사항으로 등록.
2. **내부 모순**: 섹션 간 서로 충돌하는 서술이 없는가.
3. **스코프 적정성**: 하나의 구현 계획으로 감당 가능한가, 분해가 필요한가.
4. **모호성 제거**: 두 가지로 해석 가능한 문장이 있으면 하나로 확정해 명시한다.

발견 즉시 인라인 수정한다. 재리뷰 루프는 불필요 — 고치고 넘어간다.

## 6. 종료 조건

- 사용자 승인을 받으면 호스트 절차의 다음 단계(영향도 확인, Plan 수립 등)로 넘어간다.
- 이 문서는 다음 단계를 강제하지 않는다 — 단계 전환은 호스트 지침의 게이트를 따른다.
